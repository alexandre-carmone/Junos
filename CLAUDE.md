# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`junos-web` is a Rust workspace that re-implements the deprecated KStars/Ekos web client. It is **not** an Ekos Live cloud client — it runs alongside KStars on the LAN as a transparent relay between KStars and a browser. The browser sees KStars exactly as if it had connected to ekoslive.com, but the traffic stays local.

Three crates:

- **`junos-server`** (Axum/Tokio) — local relay. KStars connects *inbound* to it; browsers connect to it; it broadcasts KStars events to all browsers and forwards browser commands to the attached KStars session. Also serves the WASM frontend from `junos-web/dist/`, and relays junos-guider to the browsers.
- **`junos-web`** (Leptos 0.7 CSR + WebGPU) — browser app. Connects to the server's `/ws` and exchanges raw Ekos Live JSON `{type, payload}` messages with KStars, and `guider_*` messages with junos-guider.
- **`junos-guider`** (Tokio around one synchronous engine thread) — a native Linux autoguider daemon, a Rust port of PHD2 2.6.14. Drives the guide camera, mount, AO and rotator through its own INDI XML client straight to `indiserver`, serves PHD2's JSON-RPC event server on `:4400` (Ekos' PHD2 client drives it unchanged) and a local WebSocket on `127.0.0.1:4410` that `junos-server` dials and relays to the Guide tab's native mode. Optional: without it the Guide tab drives Ekos' own guide module.

`kstars/` is the upstream KStars C++ source kept as a **read-only reference** for the Ekos Live wire format — never edit it, but grep it heavily when you need to know what KStars actually sends/accepts. `phd2/` is the same for `junos-guider`: the PHD2 2.6.14 source it is ported from.

## Repo layout

- `junos-server/`, `junos-web/`, `junos-guider/` — the three workspace crates (see Architecture below).
- `kstars/` — read-only upstream KStars C++ source, kept as the authoritative reference for the Ekos Live wire format. Never edit; grep heavily.
- `phd2/` — read-only PHD2 2.6.14 source (BSD-3-Clause), the reference `junos-guider` is ported from; gitignored like `kstars/` (`git clone --depth 1 --branch v2.6.14 https://github.com/OpenPHDGuiding/phd2 phd2`). Never edit; grep it before changing any guider behaviour. Every ported file's header names its PHD2 sources; `junos-guider/THIRD_PARTY.md` keeps PHD2's notices.
- `scripts/` — `precompress_dist.sh` writes `.gz` (and `.br` when brotli is on PATH) siblings next to the dist's wasm / js / css / html / catalogs (not `tycho.bin`, incompressible) so the server serves them pre-compressed; every build path calls it (`just build-wasm`, `flake.nix`, the tarball script, the PKGBUILD). Then three generators. `fetch_skymap.py` is PEP-723 self-contained (`uv run scripts/fetch_skymap.py`) and mirrors the CDS `P/DSS2/color` HiPS tree (orders 0–7 by default) plus the Mellinger panorama into `.cache/skymap/` (see "Offline sky map"); `pack_skymap.py` (plain `python3`, imports `fetch_skymap` for the scan and `info.json`) packs that mirror into `<skymap>/archive/` — one uncompressed `.tar` per `Norder{k}/Dir{d}` plus `meta.tar` and a `manifest.json` with sizes and sha256 — incrementally (a per-Dir fingerprint of count / bytes / newest mtime; stale archives deleted), and `pull URL_OR_DIR` restores it elsewhere with HTTP resume, checksum and member-name checks, then rewrites `info.json` from disk; `gen_dso_catalog.py` is plain `python3` and writes `junos-web/public/dso.bin`: OpenNGC (`openngc.csv` + `openngc_addendum.csv`) merged with Sharpless, vdB, Barnard, Lynds, Abell, Hickson, Arp and non-NGC cluster catalogs from VizieR/SIMBAD (cached in `scripts/dso_sources/`, offline unless `--refresh`), one entry per object via SIMBAD cross-ids then position, plus `dso_extra.csv` — the curated EN/FR common names, the exotic objects no catalog has, and emission-signature overrides (`lines` column, `Ha3 OIII2 SII1 RGB2`). Add a nickname, an object or a signature there, not in code. It also writes each object's IAU constellation (Roman's 1875 boundaries, VizieR VI/42, cross-checked against OpenNGC's `Const`) and its emission-line signature, derived from the kind and the catalogs' types (OpenNGC `HII`/`EmN`/`RfN`/`Neb`/`Cl+N` and Hubble type, SIMBAD otype, Sharpless vs vdB). `gen_star_tiles.py` (plain `python3`, Tycho-2 cached in `.cache/tycho2/`) writes `junos-web/public/tycho.bin`: every Tycho-2 star `junos.bin` lacks, in ~5° sky tiles. There is **no generator for `junos.bin`** — the base star catalog (names, constellation figures) is checked in and authoritative; regenerate `tycho.bin` if it ever changes. Don't regenerate outputs as part of unrelated code changes. Finally `check_i18n.py` (plain `python3`, in `just check` and CI) exits 1 listing every `translations!` key missing from `en.json` or `fr.json`.
- `packaging/` — Arch Linux package (`packaging/arch/`), portable tarball (`packaging/portable/`), and CI notes. `.github/workflows/` has `ci.yml` (mirrors `just check` and `just test`) and `release.yml` (tag-triggered two-arch build).
- `flake.nix` / `nix/` — Nix dev shell, packages, and the `services.junos-web` NixOS module. Already provided; don't propose adding one.

## Frontend tabs

`junos-web` is no longer planetarium-only. The `Tab` enum lives in `main.rs` (**not** `components/tabs.rs`, which only holds the `TabContent` router). Render order is `TABS` in `components/tab_wheel.rs`, used by both the mobile wheel and the desktop strip (`components/tab_bar.rs`):

`Profiles`, `Sky`, `Targets`, `Mount`, `Focus`, `Imaging`, `Files`, `PolarAlign`, `Guide`, `Scheduler`, `Mosaic`, `Devices` — 12 tabs. Displayed labels come from `i18n` (`tab_*` keys); `PolarAlign` renders as "Polar Align". There is no dust cap / flat panel tab (removed): the cap and panel are reached through the Devices tab, the Scheduler's queue steps and `sequence_editor/cover.rs`.

Each tab module lives directly under `components/` (some as directories: `guide/`, `imaging/`, `files/`, `scheduler/`, `sky/`, `targets/`). `SkyTab` is kept mounted (`display:none` when inactive) so its WebGPU context and catalog state survive tab switches, and `MosaicTab` so its form survives the Pick on Sky round trip; the other tabs are lazy via `<Show>`. All 12 are substantial — none is a stub any more. When extending one, grow `DeviceStore` (`ws/store.rs`) and the `apply_ekos_event` match arm only as needed.

## Build & run

```bash
# One-time
rustup target add wasm32-unknown-unknown
cargo install trunk

# Preferred — uses the repo's justfile
just               # release build (wasm + server + guider) then run the server
just build         # release build only (`build-server` builds junos-server and junos-guider)
just check         # fast typecheck of the three crates (no codegen; the guider with --features sim) + check_i18n.py
just test          # cargo test -p junos-server, then -p junos-guider
just dev-wasm      # `trunk watch` in junos-web/
just dev-server    # `cargo run -p junos-server`
just clean         # cargo clean + rm junos-web/dist

# Manual equivalents
cd junos-web && trunk build --release
cargo build --release -p junos-server -p junos-guider
./target/release/junos-server
./target/release/junos-guider                       # INDI at localhost:7624
cargo run -p junos-guider --features sim -- --sim   # the gear simulator, no INDI
cargo check -p junos-web --target wasm32-unknown-unknown
cargo check -p junos-server
cargo check -p junos-guider                         # also --features sim and --tests
```

Workspace root `Cargo.toml` sets `default-members = ["junos-server"]`, so `cargo build`/`cargo run` from the root operate on the server only (`-p junos-guider` for the guider). `junos-web` is only buildable through Trunk (or `cargo check --target wasm32-unknown-unknown -p junos-web`). The wasm is built with the `wasm-release` profile (`opt-level = "z"`, fat LTO, `panic = "abort"`; `data-cargo-profile` in `index.html`, `--profile wasm-release` in `flake.nix`), kept apart from `release` so the server keeps unwinding and a fast build.

### Server ports

`junos-server` binds **two** ports by default:

- **HTTP on `:8080`** — KStars-facing. KStars' Ekos Live client connects here.
- **HTTPS on `:8443`** — browser-facing. iOS Safari requires TLS to expose WebGPU, so the browser must hit `https://<host>:8443`. A self-signed cert is auto-generated into `.certs/` on first run.

Pass `--no-https` to skip TLS for headless/CI runs. `config.rs` (clap, env-aware) parses `--http-addr`, `--https-addr`, `--dist-dir`, and the TLS flags.

`just test` runs the server-side unit tests (`cargo test -p junos-server`) and `cargo test -p junos-guider`: the engine's unit tests (goldens from PHD2), the daemon, INDI and event-server tests against the gear simulator and a scripted `indiserver` (`indi/fake.rs`), and `tests/ekos_sequence.rs`, a TCP client replaying Ekos' `phd2.cpp` request lines against `--sim` (one reply per id, event order, app-state strings). The tests build the crate with `sim` through a self dev-dependency. A few INDI and Ekos-sequence tests wait on real time and can fail under heavy load: re-run one alone before blaming a change. `junos-web` is wasm-only — wgpu's webgpu backend does not build for the host — so its tests need a wasm runner and are not in that recipe. Everything else is verified manually: run KStars, enable Ekos Live, point it at `http://localhost:8080`, start an equipment profile (simulators are fine), open the browser to `https://localhost:8443` (accept the self-signed cert), click Start in Ekos, check the HUD shows the mount RA/Dec and the mount-anchored FOV reticle appears on the sky. For the guider: `junos-guider` against the INDI simulators (the telescope simulator unparked), the Guide tab's native mode, and Ekos with its profile's guider set to PHD2 at `localhost:4400`.

### junos-guider ports and flags

`junos-guider` listens on **`:4400`** — PHD2's event server, every interface, `4400 + instance − 1` — and on **`127.0.0.1:4410`** — the relay's socket, `4410 + instance − 1` — which `junos-server` dials (`--guider-ws`/`GUIDER_WS`, default `ws://127.0.0.1:4410`). `config.rs` (clap, each flag with an env var but the three one-shot ones):

- `--indi-host`/`INDI_HOST`, `--indi-port`/`INDI_PORT` — `localhost:7624`; the profile's `/indi/INDIhost` / `/indi/INDIport` (the Equipment sheet) win once set.
- `--instance`/`GUIDER_INSTANCE` — PHD2's `-i` (default 1): both ports and the config file (`config-N.json`). A second process of the same instance exits at once (an flock on `config[-N].lock`, PHD2's single-instance check).
- `--server-port`/`GUIDER_SERVER_PORT` (0 = ephemeral, for the tests), `--ws-addr`/`GUIDER_WS_ADDR`.
- `--data-dir`/`GUIDER_DATA_DIR` — the profile store, `darks/` and `save_image`'s folder in one place; default `$XDG_CONFIG_HOME/junos-guider/` for the store and `$XDG_DATA_HOME/junos-guider/` for the rest.
- `--log-dir`/`GUIDER_LOG_DIR` — stands for PHD2's `/frame/LogDir`; default `~/Documents/PHD2`.
- `--sim`/`GUIDER_SIM` — the gear simulator instead of INDI; needs the `sim` feature (exits 1 without it).
- `--shutdown-exits`/`GUIDER_SHUTDOWN_EXITS` — the `shutdown` RPC ends the process, as PHD2's does. Off by default: it stops capture, disconnects the gear and keeps serving, so a client's "shut down" doesn't kill a service.
- One-shot, PHD2's `-s` / `-l` / `-R`: `--save FILE` (every setting to a `PHD Config 1` file, then exit; wins over `--load`), `--load FILE` (replace every setting, then exit), `--reset` (defaults, deleting the profiles' dark libraries and defect maps, then run).

With `/ServerMode` off there is no event server. A config file that isn't the store's JSON is moved to `config.json.bad` and the guider starts as new. SIGTERM / Ctrl-C closes the guide log and disconnects the gear; a panic on the engine thread exits 1 so a service restarts. Logs go to stderr through `tracing` (`RUST_LOG`).

## Architecture

### Server (`junos-server`)

`hub.rs` is the central state. A `tokio::sync::broadcast` channel of `Arc<Outbound>` (`Text` or `Preview {kind, full, lite}`) fans KStars events out to every connected browser, plus an `Option<mpsc::Sender>` that points at the currently-attached KStars session (only one KStars can be attached at a time). Its replay cache keeps the last message per sticky type, the guide history and the latest preview per `FrameKind`, and counts the browsers wanting lite previews. junos-guider's part of it — `FrameKind::Guider` (`+J`) and the `guider_*` stickies (`guider_state`, `_settings`, `_calibration`, `_profiles`, `_devices`, `_darks`, `_ga`, `_pa`, `_tools`) — survives a KStars attach (`reset_kstars`) and goes when the daemon link drops (`forget_guider`, which keeps only `guider_state {attached:false}`); `guider_history` is not a sticky but a `GuiderHistory` rebuilt from the `guider_event`s and app-state changes (300 s, ≤ 2000, timed by the daemon's `Timestamp`), since the daemon sends it only when the link opens.

- `kstars_ws.rs` handles `GET /message/ekos` and `GET /media/ekos` (KStars connects to these as an Ekos Live "offline server"). On connect it sends KStars the `set_client_state` handshake (required — KStars drops every outbound event until it receives that) and publishes a synthetic `new_connection_state {connected:true}` to the hub. Inbound text is broadcast to browsers verbatim; binary media frames are decoded (in `spawn_blocking`) from the 512-byte metadata header plus JPEG/FITS payload and re-emitted as `new_preview_image` — an `Outbound::Preview` carrying the frame's kind, the full JSON and, while any browser asked for lite previews, a 960 px / q70 re-encode (`lite_jpeg`; KStars itself always sends 1920 px / q90, `media.h:124`). The focus star overlay is measured on the full frame and scaled onto the lite one.
- `proxy.rs` handles `GET /ws` (browser side). On connect it tells the new browser the current KStars-attached state and replays the hub's snapshot, then loops: KStars events → browser, browser commands → KStars via the hub. Previews are filtered per browser: the client sends `{"type":"junos_media_filter","payload":{"kinds":["+G"],"max_width":960,"quality":70}}` (kinds ⊆ `+F` focus, `+A` align, `+G` guide, `capture`, `+S` the live stack the relay itself publishes, `+J` junos-guider's frames; `main.rs` derives it from the active tab and re-sends it on each `connected` rising edge) and gets only those kinds — nothing until it has sent one — in the lite variant when it asked for `max_width`. A newly wanted kind is served the hub's latest frame of that kind at once. `junos_*` messages are for the relay and never reach KStars. Nor do `guider_*` ones (`guider_rpc`, recognised by a `contains("\"guider_")` pre-check then the parsed `type`): they go to `GuiderLink` through the browser's `GuiderSlot`, whose `+J` wants (frames, the star crop for the star profile, lite) are summed into the daemon's `set_frame_filter`, and only this browser gets the `Outbound::Reply` to its call. On a broadcast lag it re-sends `hub.replay_guider()` (the guider stickies and history; the daemon itself only repeats `guider_state`).
- `guider.rs` — `GuiderLink`, the link to junos-guider: dials `--guider-ws` and keeps redialling (1 s backing off to 10 s; a 5 s handshake timeout; a ping every 10 s, dropped after 30 s of silence), so the daemon runs and restarts on its own. Both ways go through bounded queues filled with `try_send`: a stalled daemon drops browser commands rather than block a browser task. Daemon text other than `guider_*` is dropped; the rest goes into the hub and to every browser unchanged, except `guider_frame` — a `+J` `Outbound::Preview` (`new_preview_image`, its overlay scaled to the JPEG like the focus stars, the lite re-encode through `lite_jpeg`, at most 2 frames waiting) — and `guider_rpc_result`, unwrapped from the `"b{slot}:{id}"` id the browser's call was given and sent to that browser only. While the daemon is away a call is answered at once with `-32603`; when the link drops, browsers get `guider_state {attached:false}`.
- `auth.rs` is a stub for `POST /api/authenticate` (no real auth — local relay only).
- `config.rs` parses the clap `Config` (all long-only flags, each with an env var): `--http-addr`/`HTTP_ADDR`, `--https-addr`/`HTTPS_ADDR`, `--dist-dir`/`DIST_DIR`, `--captures-dir`/`CAPTURES_DIR`, `--skymap-dir`/`SKYMAP_DIR`, `--skymap-online`/`SKYMAP_ONLINE`, `--taskqueue-dir`/`TASKQUEUE_DIR`, `--guider-ws`/`GUIDER_WS`, `--tls-cert`, `--tls-key`, `--no-https`. Also `resolved_captures_dir()` / `resolved_skymap_dir()` / `resolved_taskqueue_dir()`.
- `tls.rs` — cert/key resolution and self-signed generation into `.certs/` (`CN=junos-dev`, SANs = localhost + 127.0.0.1 + every non-loopback IPv4). Supplying only one of `--tls-cert`/`--tls-key` is a fatal error.
- `files.rs` — the Files tab's backend: `/api/files/{list,meta,thumb,raw,download,rename,delete,resolve,mkdir}`, FITS header parsing and thumbnailing (a three-plane cube, KStars' colour stack, renders RGB). Sandboxed to the resolved captures dir by canonicalize checks. `starfind.rs` is the star detector `kstars_ws.rs` runs on focus frames for the Focus tab's star overlay.
- `apps.rs` — `/api/apps/{launch,stop,state,power,guider}`: spawn and monitor KStars, PHD2 or junos-guider on the server host (executables on PATH, or found running through `/proc/*/comm`; `app_state {kstars, phd2, junos_guider}`). PHD2 and junos-guider both serve :4400, so either launch is refused while the other runs; a launched junos-guider gets `--ws-addr` from `--guider-ws` (and no INDI flags: the profile's server, else `localhost:7624`), and it counts as running whenever `GuiderLink` is attached, wherever it runs; `power {action: poweroff|reboot}` runs `systemctl <action>` as the server's user (logind + polkit decide — the NixOS module's `hostPower.enable` and the Arch polkit rule grant it to service installs); `guider {action: connect|disconnect}` runs `dbus-send` against KStars' `/KStars/Ekos/Guide` `connectGuider`/`disconnectGuider` — the Guide tab's Connect PHD2 button, since Ekos Live has no such command and `option_set GuiderType` changes nothing live (`Guide::processGuideOptions` is never called).
- `stack.rs` — the live stack relay. KStars never sends the stacked image over Ekos Live: it writes `<outputDirectory>/stacked_frame_NNNN.fits` after each sub for the cloud server to pick up, and `StackWatch` is that server. It follows the stacker's state and output folder in the KStars text the message handler relays (`livestacker_get_all_settings`, `new_livestacker_state`: `started` → watching, `stopped` / `closed` / `initialized` → not), polls the folder once a second while a stack runs, publishes each new frame as a `+S` `Outbound::Preview` built like a media frame (`kstars_ws::stack_preview`: `fits_to_jpeg` at 1920 px, the lite variant, `last_preview` replay) and prunes the folder to the newest two files. Polling, not events: `complete` is emitted before the file is written, and after a `restarted` KStars overwrites `stacked_frame_0000.fits` in place, so a frame is new by (path, mtime, size) and is published once that triple has held for two polls.
- `skymap.rs` — serves the offline sky map, a local HiPS mirror, at `/api/skymap/*` (see "Offline sky map" below): `info` (JSON, `no-cache` + weak ETag → 304; derived from a startup directory scan into `AppState.skymap` when `info.json` is missing), `properties`, `Norder{k}/Dir{d}/Npix{n}.jpg` tiles (`parse_tile` validates the three segments and rebuilds the path from the numbers; `immutable` for a year + strong ETag), `allsky.jpg` / `allsky_small.jpg` (a day). With `--skymap-online`, a missing tile is fetched from the CDS mirrors (reqwest, `Semaphore(4)`), stored in the tree and served; failure → 502 `no-store`. `main.rs` also serves `<skymap-dir>/archive/` as-is at `/api/skymap/archive/*` (a `ServeDir` merged outside the compression layer, Range requests honoured) — the archives `scripts/pack_skymap.py pack` writes, for `pack_skymap.py pull` on another machine.
- `http_cache.rs` — the `Cache-Control` middleware for the static frontend: `index.html` → `no-cache`; the Trunk-hashed wasm / js / css and the three `*.bin` → `immutable` for a year (the catalogs are fetched with a `?v=` the client bumps on regeneration). `/api/*` is left to its handlers. `main.rs` puts every HTTP route under it and under tower-http's `CompressionLayer` (br/gzip, level 4), with `ServeDir::precompressed_{br,gzip}` serving the siblings `scripts/precompress_dist.sh` wrote; the three WebSocket routes sit outside both.
- `taskqueue.rs` — `/api/taskqueue/{list,queue/:name,script/:name}`: reads/writes the KStars task-queue collections (`collections/*.json`, a `tasks` collection or an `items` queue) and their shell scripts (`scripts/*.sh`, chmod 0755) that the Scheduler's startup/shutdown queue editor builds. Slug names only; reserved `observatory_startup`/`observatory_shutdown`.
- `planning.rs` — `/api/planning/{list,raw,rename,delete}` for Files › Planning: four flat folders keyed by `kind` — `schedules` (`~/.junos-schedules/*.esl`), `sequences` (`~/.junos-sequences/*.esq`), `queues` / `scripts` (the task-queue dir). Bare file names with the kind's extension, canonicalize-checked; only schedules can be renamed (the others are referenced by absolute path), reserved queues can't be deleted. `main.rs` creates both `~/.junos-*` folders at startup, since KStars' `QFile` won't — KStars is assumed to run on the same host as the same user.
- `main.rs` — also serves `GET /api/config`, which reports the resolved captures dir. The frontend reads it once into `CaptureDirCtx` so the sequencer forms default to a folder the Files tab can browse.

There is **no protocol translation** in the server. Messages flow through opaque. All Ekos Live semantics live in the WASM client. Two exceptions: the `junos_*` control family (`junos_media_filter`, above), consumed by `proxy.rs`; and junos-guider's `guider_*` traffic (`guider.rs`), which the relay routes itself — `guider_rpc` ids wrapped per browser so each `guider_rpc_result` reaches only its caller, `guider_frame` turned into a `+J` `new_preview_image`, `guider_history` rebuilt from the events for the replay.

### Guider (`junos-guider`)

A port of PHD2 2.6.14 under **strict behavioural parity**: whatever a PHD2 client, the guide log or PHD2 Log Viewer can observe is PHD2's, quirks included (pitfall 24). Every ported file opens with `Ported from PHD2 src/… — BSD-3-Clause, see THIRD_PARTY.md`; the crate is `GPL-3.0-or-later AND BSD-3-Clause`. `main.rs`: flags (above), the instance lock, `--save`/`--load`/`--reset`, the profile store, then `Daemon::start`, `ws::spawn`, `EventServer::start` (in server mode), and wait for a signal, a `shutdown` with `--shutdown-exits`, or an engine panic.

- `engine/` — PHD2's `MyFrame` and worker thread as **pure, synchronous** code: no I/O, no async, no wall clock. Devices come in through traits, time through `traits::Clock`, files through `Files`, and everything goes out as `EngineEvent`s, so the whole engine runs headless on the simulator in the tests. `mod.rs` is `Engine`, whose `step()` follows `myframe_events.cpp`: the queued moves, the exposure delay, the capture (dark or defect map, noise reduction, stats), `UpdateGuideState` through the controller, then the frame's moves (pMount's step, an AO's bump on the mount right after) and `OnMoveComplete`. `command.rs` holds `Command` (one per mutating RPC, plus the UI's extras) and the `Gear` the daemon hands in; `event.rs` holds `EngineEvent` (the 27 PHD2 events plus the frame, guide-log line, status and notice) and the `Snapshot` the read-only RPCs answer from; `session.rs` the files, the event → log-writer map, and the connect / disconnect side effects. Building blocks:
  - `traits.rs` (Rect, Dir, Point, PierSide, Clock, CancelToken), `rng.rs` (xorshift64*), `image.rs` (`UsImage`, u16, and PHD2's image math), `fits.rs`, `star.rs` (`Star::find`, HFD, AutoFind), `stats.rs`.
  - `algo/` — Identity, Hysteresis, Lowpass, Lowpass2, ResistSwitch, ZFilter (`zfilter_factory.rs`, the mkfilter port) and `gp/`, Predictive PEC (kernels, period estimate, `linalg.rs` with Eigen's pivoted LDLT).
  - `calibration.rs`, `mount.rs` (the move pipeline, `GuideStepInfo`), `scope.rs` (`move_axis`, the calibration state machine), `backlash.rs`, `stepguider.rs` (AO calibration and bumps), `camera.rs` (`GuideCamera`, the On-camera ST-4 mount).
  - `multistar.rs`, `guider.rs` (the state machine, lock position, lock shift), `control.rs` (`PhdController`: guide / dither / settle, pauses, auto-exposure), `darks.rs` (dark library, defect map), `assistant.rs` (Guiding Assistant).
  - `tools/` — the secondary tools' pure state machines: polar drift, static PA, drift align, calibration assistant, pier-flip, star-cross, comet training, bookmarks. `windows.rs`, `secondary.rs` and `*_win.rs` drive them.
  - `log/` — `cfmt.rs` (C `%g` / `%.*f`), `guide_log.rs` (PHD2 log v2.5, byte for byte), `debug_log.rs`, `image_log.rs`.
  - `engine_tests.rs` and `testdata/*_phd2.txt` — goldens from throwaway C++ harnesses built against `phd2/` (never committed).
- `sim/` — PHD2's gear simulator: a camera, a mount (PE, seeing, backlash, drift, pier side) and an AO. Built under `cfg(test)` or the `sim` feature (`--sim`).
- `daemon/` — `Daemon`. The engine runs on one `std::thread`. `Command`s come in with a reply channel, answered after the snapshot is published and the events are broadcast (PHD2's order). Events go out on a `broadcast`; the latest frame and the `Snapshot` sit in `watch`es, so `get_app_state` and the other read-only RPCs never wait for an exposure. A 1 s tick sends `Command::Tick`, writes the profile when it changed and polls the gear. `stop_capture`, `set_connected false` and shutdown cut a capture or pulse short through the engine's `CancelToken`. `gear.rs` builds and connects the gear off the engine thread, in PHD2's order: camera, AO, mount, aux mount, rotator. The INDI devices share one `IndiClient`; `loop` and `guide` answer code 1 meanwhile. After an INDI drop it connects the gear again. `files.rs` covers the disk and the log folder.
- `indi/` — the INDI client, PHD2's libindiclient side:
  - `xml.rs` is the tokenizer and writer (XML entities, `.z` BLOBs).
  - `store.rs` is the property store, with a sequence number per change: a pulse waits for `seq > seq0 && state != Busy`.
  - `client.rs` owns the socket: a reader thread, `pingReply`, `getProperties` per device, `enableBLOB` naming the property, and a reconnect from 250 ms backing off to 8 s.
  - `camera.rs` (the `CCD1` / `CCD2` chip, compression off, FITS, ST-4), `mount.rs` (`TELESCOPE_TIMED_GUIDE_*`, a motion-rate fallback, the pointing source, the aux mount), `ao.rs`, `rotator.rs`.
  - `fake.rs` is a scripted `indiserver` for the tests.
  - Equipment is named as PHD2 names it (`INDI Camera [<dev>]`, …), because Ekos matches the camera name. `/indi/PulseMinWait` (on by default) sleeps out a pulse that a driver answers at once.
- `server/` — PHD2's event server:
  - `rpc.rs` is the protocol without the sockets: line framing, batches, PHD2's error texts, and `METHODS`. That table holds the **54 PHD2 methods** in `event_server.cpp`'s order, then the 76 `ws_only` extras the TCP server answers with `-32601`.
  - `methods.rs` answers the 54. It checks the params with PHD2's texts, then sends a `Command`, or answers from the snapshot: `clear_calibration`, `deselect_star`, `get/set_exposure`, `get_exposure_durations`, `get_profiles`, `get/set_profile`, `get/set_connected`, `get_calibrated`, `get/set_paused`, `get/set_lock_position`, `loop`, `stop_capture`, `guide`, `dither`, `find_star`, `get_pixel_scale`, `get_app_state`, `flip_calibration`, `get/set_lock_shift_enabled`, `get/set_lock_shift_params`, `save_image`, `get_star_image`, `get_use_subframes`, `get_search_region`, `shutdown`, `get_camera_binning`, `get_camera_frame_size`, `get_current_equipment`, `get/set_guide_output_enabled`, `get_algo_param_names`, `get/set_algo_param`, `get/set_dec_guide_mode`, `get_settling`, `guide_pulse`, `get_calibration_data`, `capture_single_frame`, `get_cooler_status`, `set_cooler_state`, `get_ccd_temperature`, `export_config_settings`, `get/set_variable_delay_settings`, `get/set_limit_frame`.
  - `extras.rs` answers the UI's own: profiles and `set_profile_value`, `set_equipment`, algorithms, darks and BPM, the GA, the polar tools, the calibration assistant, pier-flip, star-cross, nudge and bookmarks, comet, dither / auto-exposure / image logger, and `list_logs` / `read_log` (the last `tail` bytes, or the file in 1 MiB chunks of whole lines from `offset`, `next` giving the following one: a debug log can pass the relay's 16 MiB frame). `connect_device` (`Daemon::connect_device`) is one device's Connect / Disconnect from the gear dialog.
  - `events.rs` writes the 27 events with their members in PHD2's order, and the catch-up sent on connect: Version, LockPositionSet, StarSelected, CalibrationComplete, StartGuiding | StartCalibration | Paused, AppState.
  - `mod.rs` is the listener: every interface, `SO_REUSEADDR` and `SO_KEEPALIVE`, `\r\n` lines, one task per client, requests run one at a time, the events a command raised sent before its reply, and a client that stops reading dropped after 30 s.
- `ws.rs` — the relay's socket (`--ws-addr`). Snapshots go to each new connection (`guider_state` first), then whenever their text changes:
  - `guider_state` — app state, gear, lock and star, exposure, pixel scale, settling, `port` / `port_error`, …; sent again every 5 s while capturing or a tool runs.
  - `guider_settings` — every profile key under PHD2's name, plus `algo_params` and the two globals the UI edits.
  - `guider_profiles`, `guider_calibration`, `guider_devices`, `guider_darks`, `guider_ga`, `guider_pa` (`drift`, `static`, `drift_align`), `guider_tools`.
  - `guider_history` — the last 300 s (≤ 2000) of guide steps, calibration steps and state changes; on connect and on `get_history` only.

  Deltas: `guider_event` (the PHD2 event as the TCP server writes it), `guider_alert {Type, Msg}`, `guider_log {line}` (guide-log INFO and calibration lines, never the debug log). Calls: `guider_rpc {method, params, id}` → `guider_rpc_result {id, result | error{code, message}}`, through `methods::run` (extras included), each call in its own task. The socket's own methods are `set_frame_filter {frames, profile, max_width, quality}` and `get_history`. `guider_frame {seq, metadata, data, stats, guider{lock, star, stars, search_region, lock_shift_px_h, star_image}}` goes out only while the relay asks: a JPEG stretched as PHD2 displays the frame (filtered min/max, `/Gamma`), the overlay in frame pixels, and with `profile` the 16-bit crop `get_star_image` gives. A frame that comes while the last one encodes is dropped. `shutdown` here never ends the process.
- `profile.rs` — PHD2's wxConfig tree in one JSON file, `config.json` (`config-N.json`): `{version, current_profile, global{"/ServerMode", "/frame/LogDir", …}, profiles{"<id>": {name, values{"/scope/CalibrationDuration": …}}}}`. Key names are PHD2's, verbatim and case-insensitive; doubles are kept as their `%g` text, as wxFileConfig does. The file is written atomically (tmp + rename), only when something changed, and every change is one leading-edge `ConfigurationChange`. Import / export: `PHD Profile 1` (one profile, `.phd`) and `PHD Config 1` (everything; `export_settings`, `--save`, `--load`).
- Files keep PHD2's names. Under `<data>/darks/`: `PHD2_dark_lib[_N]_<id>.fit`, `PHD2_defect_map[_N]_<id>.txt` and the `PHD2_defect_map_master*` FITS. In the log folder (`--log-dir`, else `/frame/LogDir`, else `~/Documents/PHD2`, else `~/Documents`):
  - `PHD2_GuideLog_[N_]<date>_<time>.txt` — log v2.5, opens in PHD2 Log Viewer. Always on, as in 2.6.14 (`/LoggingMode` is written, never read). A new file with nothing meaningful in it is deleted at close. Kept 60 days.
  - `PHD2_DebugLog_…txt` — kept 30 days.
  - `[N_]PHD2_CameraFrames_<stamp>/` — the image logger's.
  - Both logs roll over on the first guide start of a new imaging day (09:00 to 09:00). The Logs sheet reads them through `list_logs` / `read_log {name, tail}`, and downloads one through `read_log {name, offset}`, chunk by chunk.

## Ekos Live wire format

JSON `{"type": "...", "payload": {...}}` over WebSocket. Authoritative references:

- **`kstars/kstars/ekos/ekoslive/commands.h`** — the enum of ~200 message types. Name list.
- **`kstars/kstars/ekos/ekoslive/message.cpp`** — handlers. Read this first when extending the client. Especially `processTextMessage()` (top of the big command switch), `processDeviceCommands()` (line 1652), `updateMountCoords()` in `manager.cpp:3173`.
- **`kstars/kstars/indi/indistd.cpp`** — `numberToJson`, `switchToJson`, `textToJson`. This is how `device_property_get` / `device_property_set` payloads are serialized.

### Critical pitfalls — *read these before adding features*

1. **Two gates, not one.** `new_connection_state` carries `{connected, online}`. `junos-server`'s synthetic event only sets `connected`. KStars' real event after profile start sets `online: true`. Many endpoints (`get_devices`, `get_states`, `get_scopes` in most call sites, `process*Commands`) gate on `getEkosStartingStatus() == Success` and are silently dropped before that — see `message.cpp:264, 291`. `ws/` prime requests fire on `online=true`, not `connected=true`, for this reason.

2. **`m_ClientState`.** KStars' `Node::sendResponse` (`node.cpp:156`) drops every outbound event if the remote peer hasn't sent `{"type":"set_client_state","payload":{"state":true}}`. `junos-server/src/kstars_ws.rs` sends this on connect; don't remove it.

3. **`processDeviceCommands` silent drop.** `message.cpp:1664` — `if (!INDIListener::findDevice(device, …)) return;`. If the INDI driver for a device isn't registered yet when you send `device_property_get` / `device_property_set` / `device_property_subscribe`, the command is dropped with no reply and the subscription is not recorded. This is why `ws/retry.rs::spawn_retry_property` exists: it keeps firing subscribe+get for up to 60 s until the expected data actually lands in the store.

4. **Mount coordinates come from a timer, not a signal.** `kstars/indi/indimount.cpp:244` — `updateCoordinatesTimer.start()` is only called after the first `processNumber(EQUATORIAL_EOD_COORD)` arrives from INDI. For idle drivers that don't push until something changes (e.g. Telescope Simulator at rest), `new_mount_state` carries `{status, target, …}` but **no RA/Dec** until the user triggers movement. The retry fetches `EQUATORIAL_EOD_COORD` directly via `device_property_get` to short-circuit this.

5. **`new_mount_state` is sent from multiple places.** Coord updates (full payload `{ra, de, ra0, de0, az, at, ha, …}`, throttled to 1 s in `message.cpp:2552`) vs status-only updates (`{status}`, `{target}`, `{pierSide}`, …). Match arms must tolerate partial payloads.
6. **Scheduler "script" slots take task-queue JSON, not scripts.** In KStars 3.8+ `schedulerPreStartupScript`/`schedulerPostStartupScript`/`schedulerPreShutdownScript`/`schedulerPostShutdownScript` are absolute paths to task *collections* (`QueueManager::loadQueue`); a shell script only runs as a `script_execute` task inside one, and must be executable with a shebang. KStars silently drops a task with an unknown `template_id` or a missing/out-of-range parameter, and a device task in the pre-startup or post-shutdown slot (INDI down) stalls the scheduler — `components/scheduler/queue_model.rs` mirrors `kstars/kstars/data/taskqueue/templates/system/*.json` and enforces all three. A collection can only name templates, so a queue with a custom INDI step is written in KStars' own queue format (`{"items":[{"task":{…,"actions":[…]}}]}`, `queue_native.rs`, built-in steps spelled out from a copy of the templates' actions); `loadQueue` reads both. That format ignores a task's `failure_action` for a missing device — it always aborts the queue.
7. **Module logs arrive newest first.** `new_guide_state {log}`, `new_scheduler_state {log}` and `new_capture_state {log}` carry `getLogText()`, and KStars prepends each entry (`Guide::appendLogText`, `SchedulerProcess::appendLogText`, `Capture::appendLogText`). Show them as-is; the latest line is the first one.
8. **`scheduler_save_file` can silently write nothing.** `Scheduler::save` (`scheduler.cpp:2304`) skips the write when the job list hasn't changed since it was last saved or loaded, then the handler replies with whatever file already sits at that path — or not at all. Its reply, like those of `scheduler_load_file` and `capture_load_sequence_file`, lands in `DeviceStore::file_reply` (`ws_helpers::file_command` sends and waits); Save schedule trusts only the file's mtime moving.
9. **`scheduler_import_mosaic` empties the job list.** `FramingAssistantUI::createJobs` (`framingassistantui.cpp:653`) calls `removeAllJobs()` before adding the tiles, so the Mosaic tab never uses it: Send to Scheduler lays the tiles out itself (`sky::derive_planner_mosaic_plan`, the sky's preview) and adds one job per tile like Add job does (`scheduler_set_all_settings` + `scheduler_add_jobs`), all sharing one `.esq`. KStars inserts an added job below the selected row, not at the end.
10. **An `.esq` head overwrites Ekos' Capture limits.** Whenever Capture loads a sequence (each Scheduler job start, `capture_load_sequence_file`), `SequenceQueue::setOptions` copies its `<RefocusEveryN>`, `<RefocusOnTemperatureDelta>`, `<RefocusOnMeridianFlip>`, `<HFRCheck>`, `<GuideDeviation>` and `<GuideStartDeviation>` into KStars' global options, where they stay. Leaving an element out doesn't keep Ekos' value: the `m_*Set` flags are never reset, so the last loaded file's value is applied again. `build_esq_xml` therefore always writes all of them from `SeqLimits`. Dithering is per row (`<GuideDitherPerJob>`: 0 = the Guide module's frequency, N, −1 = never); the Guide module's "Enable dithering" stays the master switch.
11. **A sequence ending on calibration frames leaves the panel lit and the cap closed.** KStars lights the panel and parks the cap before flats, and undoes both only before the next light frame (`SequenceJobState::checkLightFrameScopeCoverOpen`); the end-of-capture "light off" in `CameraProcess::stopCapturing` checks a flag nothing sets. `sequence_editor/cover.rs` fills the gap with a `<PostJobScript>` on the last row: a shell script, written through `/api/taskqueue/script` (KStars runs it with no shell or arguments, JSON on stdin), that calls KStars' D-Bus API (`getDevicesPaths`, `LightBox.setLightEnabled`, `DustCap.unpark`) — so it needs no device names and no INDI host.
12. **The Filter Settings table is request/reply only, and a write is all-or-nothing.** `fm_get_data` answers under its own type with the Capture *main camera's* FilterManager table (`message.cpp:1806`, `filtermanager.cpp:952`); `FilterManager::updated()` reaches nothing, so the client asks at bootstrap, in the 20 s sweep and after each write. `fm_set_data` has no reply, is ignored unless `device` matches, overwrites every column of every row it gets (a missing `lastafdt` becomes the literal `"yyyy-MM-dd hh:mm:ss"`), crashes KStars on an out-of-range `index`, and rewrites INDI `FILTER_NAME` — always round-trip whole rows. Build Filter Offsets (`filter_offset_*`) addresses the *alphabetically first* wheel (`manager.cpp:4420`), accepts only `adaptFocus`, `refFilter` and positional `numFocusRuns`, runs through `invoke_method` on the headless `BuildFilterOffsets:<wheel>` (never `showDialog`, it is modal), re-initialises only from the desktop dialog (one clean run per session) and asks a failed autofocus's Stop/Retry on the desktop (`KMessageBox`, not relayed). `components/filter_offsets.rs` states all three.
13. **`option_get` / `option_set` want the Q_PROPERTY name, not the kcfg entry.** kconfig_compiler generates the property from the entry with its first letter lowercased (`PHD2Host` → `pHD2Host`, `SolverType` → `solverType`); a wrong name reads null and writes a dynamic property nobody reads, with no error either way. `option_set` saves and answers nothing, so re-ask with `option_get`; every reply entry lands in `DeviceStore::options`. The plate solver's type (`solverType`, `SSolver::SolverType` index) and options profile (`solveOptionsProfile`, an index into `get_stellarsolver_profiles`' `align` list) live there, not in `align_get_all_settings`: Align reads them at solve time (`align_solver.cpp:553, 567`). A profile's parameters (threads, scale range) are not reachable over Ekos Live — only the pick.
14. **The Live Stacker's image never crosses Ekos Live, and its events mislead.** `livestacker_*` (message.cpp:3401) is gated on Ekos started. KStars writes each stacked frame to `<outputDirectory>/stacked_frame_%04d.fits` (`fitsview.cpp:803`) and expects the server to watch the folder (`junos-server/src/stack.rs`); `new_livestacker_state {state:"complete"}` fires after every stack update, after a cancel and on a failure — *before* the file is written — and `restarted {target, filter}` (the next sequence job) resets the counter so `0000` is overwritten in place. `livestacker_start` connects its progress signals without `UniqueConnection`, so always `livestacker_initialize` first (it closes the previous viewer). In loop mode KStars saves each preview frame into `stackingDirectory` but never creates it, and its directory watcher fails silently on a missing folder; in sequence mode it replaces `stackingDirectory` with the running job's folder. While a stack runs, no capture frame is sent over media (`media.cpp:768`). Settings live only in KStars' memory (`m_LiveStackerSettings`).
15. **The Aberration Inspector is a KStars fork, and its start reply is not the first status.** `focus_abins_*` exists only in the user's fork (`/home/alexandre/Projects/kstars`, `message.cpp processAbInsCommands`; upstream KStars drops them), gated on Ekos started, on the main focuser. `focus_abins_start` *pushes* a `focus_abins_status {running:true}` before its reply, which is the same type plus `startAccepted` (and `error` when refused) — match on that key, never on the first status. `focus_abins_status` is also sent in `get_states` (so the bootstrap and the 20 s sweep fetch it), pushed after analysis (`lastRunState:"complete"`, right after the pushed `focus_abins_result`) and at `stop()` (`running:false`; `aborted` keeps the previous result). `canStart` needs an absolute focuser, Linear 1 Pass, the mosaic mask and a non-quadratic fit (`reasons` carries the codes). Both `focus_abins_get_all_settings` and `focus_abins_set_all_settings` reply under **`focus_abins_get_all_settings`** with the effective map; an invalid value (`tiltRadius` outside 5–100, `tiltScrewPitch` outside 0.1–2, a bool for an int) is dropped silently, radius / pitch / thread are refused while a Wanderer ETA is connected on a 3-point plate, and `tiltThreadIndex` does not update `tiltScrewPitch` the way the desktop widget does — `abins.rs` sends both. `focus_abins_set_all_settings` saves the plate settings but never rebuilds `focus_abins_result`'s `tiltPlate` (computed once at the end of the run, `Focus::buildAbInsResult`) — the client recomputes it. No media: the mosaic montage comes as ordinary `+F` focus frames.

The next ones are junos-guider's — PHD2's protocol and behaviour rather than Ekos Live, but they bite the same way.

16. **The AO's `CalibrationComplete` never goes out live.** PHD2 only logs it (`stepguider.cpp:762`); a client sees it only in the catch-up on connect, with `Limit`. `AppState` is catch-up only too (`NotifyAppState` has no caller): follow the state from the other events, `get_app_state` or `guider_state.app_state`. Both are parity (pitfall 24) — don't add the missing events.
17. **`:4400` is PHD2's port, and a taken port is retried, not fatal.** junos-guider and a real PHD2 both listen on `4400 + instance − 1`. On `EADDRINUSE` the daemon keeps the engine and the relay socket up, binds again after 1 s, doubling to 60 s, and publishes the error as `guider_state.port_error` (`port` is null meanwhile) — exiting would only have systemd restart it into the same conflict. An Ekos talking to a PHD2 that still holds :4400 looks like it talks to the daemon: check `port_error`. `apps.rs` refuses to launch either one while the other runs. A taken relay socket (`--ws-addr`) is only logged, not retried: the relay then never attaches.
18. **Profile keys are PHD2's names, verbatim.** `guider_settings`, `set_profile_value` and the profile files use PHD2's wxConfig keys (`/scope/CalibrationDuration`, `/guider/StarMinHFD`, `/indi/INDIcam`, `/frame/focalLength`, …), the profile's relative to `/profile/<id>`, the globals absolute (`extras::GLOBAL_KEYS` routes the two the UI edits, `/StickyLockPosition` and `/server/guide_allow_recalibrate`, to the global section). `set_profile_value` stores any key that starts with `/`, so a misspelt one is a new entry nothing reads, with no error — the same trap as pitfall 13. Take the name from `phd2/src` (`pConfig->Profile.Get*`) or from a `guider_settings` echo. Values come back as wxFileConfig text would (`%g`: six significant digits). Renaming a key also breaks `PHD Profile 1` / `PHD Config 1` files exchanged with PHD2.
19. **The algorithm methods act on `pMount`: the AO when one is connected.** `set_algo_param`, `get_algo_param*`, `set_algorithm`, `reset_algo_params` and `get/set_guide_output_enabled` address PHD2's primary mount. With an AO, `ra`/`x` and `dec`/`y` are the AO's axes, and the mount's algorithms are reachable only through `set_profile_value` — as the Algorithms sheet does. `set_algo_param` without `value` answers "expected param value param" where PHD2 crashes (fixed).
20. **`get_pixel_scale` is `null` at exactly 1.0.** 1.0 is PHD2's value for an unknown focal length or pixel size, and its event server writes `null` for it (so does a rig that truly has 1.0″/px). Ekos then logs "Pixel Scale is invalid" and falls back on its own train's pixel size and focal length; `guider_state.pixel_scale` is null and the native tab shows px. Set the focal length and pixel size in the Equipment sheet.
21. **No legacy socket server on `:4300`.** PHD2's binary protocol (`4300 + instance − 1`) is not ported; only the JSON-RPC event server is. A client that needs it gets nothing.
22. **Ekos switches to the daemon only through the KStars profile, and a profile restart.** Ekos takes its guider type, host and port from the equipment profile when the profile starts (`manager.cpp:1266, 1343`); `option_set guiderType` or `pHD2Port` writes the option and changes nothing live. "Use junos guider" (`guide/settings.rs`) therefore sends `profile_update` with `guiding: 1` (PHD2), `remote_guiding_host: "localhost"` and `remote_guiding_port` = `guider_state.port`, and asks for a profile restart; then Connect (Ekos' button, or the native footer's Connect Ekos → `/api/apps/guider`). The profile's ports go as **strings**: `ProfileEditor::setSettings` reads `remote_port` / `remote_guiding_port` with `QJsonValue::toString(default)` (`profileeditor.cpp:539, 542`), so a JSON number silently becomes 7624 / 4400 (`ProfileInfo::to_json`). Once Ekos is connected (`online`, `guiderType == 1`, its guide status neither empty nor `Disconnected`), the native Guide sends `guide_start` so Ekos' own sequence logic stays in charge, and Stop sends `guide_stop` only in the states `Guide::abort()` acts on (`EKOS_ABORTS`, `guide.cpp:1071-1095`); everything else stays native `guider_rpc`. With Ekos' auto-star off, Ekos moves the lock to its own tracking box once guiding starts (`guide.cpp:1769`).
23. **Exactly one reply per JSON-RPC id.** Ekos keeps one call in flight and waits for its reply: a lost reply stalls its PHD2 client for good. Each request line is answered whatever its handler does (`rpc::Parsed::reply`; a `ReplyGuard` answers `-32603 internal error` when dropped, after a panic too), with the `id` echoed verbatim; a notification (no `id`) gets nothing; the events a command raised go out before its reply (Ekos reads `SettleDone`, `Paused`, … in that order). A non-finite number is written `null`: PHD2's bare `nan` makes Ekos' `QJsonDocument` drop the whole line, the same stall. Over the relay, the browser gives a `guider_rpc` up after 10 s, and `GuiderLink` answers `-32603` at once while the daemon is away.
24. **Strict parity: the quirk ledger lives in the code.** Whatever a PHD2 client, the guide log or Log Viewer can observe is PHD2's, bugs included: `set_lock_position` refused with `-32600`, `GuidingStopped` after the in-flight move's `GuideStep`, `CalibrationFailed {Reason:"Calibration manually stopped"}`, `DescriptiveStats`' raw S and `DBL_MIN` max, a weak star's `snr = 2.9`, PHD2's typos in tool texts ("cannnot", "sucessfully"). Only unobservable bugs are fixed (`Fixed`: the GP's points-for-approximation key read both ways, written `_for_`; Lowpass2's stale member; the simulator's drift sign). Deliberate additions: INDI auto-reconnect, `PulseMinWait`, the bind retry, `--shutdown-exits`. Two observable deviations replace a PHD2 freeze and a null dereference: the GA's `GetMinMoveRecs` windowing and the GA without a mount. Each spot says `Quirk kept`, `Kept as PHD2 does it`, `Fixed` or `Deliberate addition`, and module docs list theirs. Before "fixing" a number that looks wrong, read those notes and `phd2/src`, and compare with a log from a real PHD2 2.6.14; keep `engine/` pure and PHD2-faithful.
25. **Tests lower `/guider/StarMinHFD` on the simulator.** The gear simulator's stars measure about 1.6 px HFD, at PHD2's 1.5 px floor: one centred on a pixel measures under it and is dropped as too small. Every simulator rig (`engine_tests.rs`, `daemon/tests.rs`, `server/tests.rs`, `tests/ekos_sequence.rs`) sets it to 1.0 in the profile, with short exposures and a quick RA-only calibration. Copy that block into a new rig, and do the same for a `--sim` run by hand (`set_profile_value`); don't change the simulator's stars or PHD2's default instead.

### Where FOV inputs actually live

- **Focal length + aperture** → `get_scopes` (OAL scope DB, keyed by `name`). Cross-reference the active train's `scope` field against this list. *Not* in `train_settings_get`.
- **Pixel size + sensor WxH** → INDI `CCD_INFO` number property on the camera device. Fetch via `device_property_get {device, property:"CCD_INFO"}`. Element names: `CCD_MAX_X`, `CCD_MAX_Y`, `CCD_PIXEL_SIZE_X/_Y` (fallback `CCD_PIXEL_SIZE`).
- **`train_settings_get` is a red herring** — it returns `OpticalTrainSettings` (a map keyed by module-enum IDs like `"0"`, `"1"`, storing per-module configs), not hardware specs. Don't add arms that parse `focalLength`/`pixelSize` from it; those fields will never exist.
- **Active train** → `train_get_all`, take `trains[0]`. Fields: `{id, name, mount, camera, scope, guider}`.

### Adding a new device control

1. Find the message in `commands.h` and read its handler in `message.cpp` to learn the payload schema. If it's an INDI property, read `indistd.cpp::{numberToJson, switchToJson, textToJson}` for the exact wire shape (compact vs non-compact).
2. If KStars *sends* it, add a match arm in `ws/store.rs::apply_ekos_event` and add fields to the relevant `*StatusData` struct.
3. If the browser *sends* it, dispatch via `send(serde_json::json!({…}).to_string())`. For INDI properties that may arrive before the driver is registered, use the `spawn_retry_property` pattern.
4. To expose new state to the planetarium, plumb it through `compat.rs` (the `*Snapshot` types consumed by `SkyTab`).

## Styling

**Component styling is inline Tailwind utility classes in the `.rs` sources.** Per-component CSS files (`styles/components/*.css`, `shell.css`) have all been migrated away and no longer exist — do not add new ones.

`junos-web/index.html` links exactly four stylesheets via `<link data-trunk rel="css" …>`, in this order:

`styles/tokens.css` → `styles/base.css` → `styles/tailwind.css` → `styles/responsive.css`

- `tokens.css` — design tokens (`--bg`, `--text-blue`, `--accent-cyan`, `--sp-*`, `--r-*`, `--fs-*`, `--font-mono`). Reference via `var(--name)` rather than restating hex/px literals; Tailwind's config maps utilities onto these.
- `base.css` — element defaults and the handful of genuinely global rules.
- `tailwind.css` — **generated, do not edit**. A Trunk `pre_build` hook runs `junos-web/bin/tailwindcss` (v3.4.17 standalone, fetched by `just setup-tailwind`) over `styles/tailwind.input.css` with `tailwind.config.js`. `Trunk.toml` ignores it in watch mode.
- `responsive.css` — the single home for hand-written `@media` rules, for the cases Tailwind's breakpoint prefixes don't cover.

In Leptos `view! {}`, style with Tailwind utilities in `class="…"`, and use `class:foo=move || cond` for state toggles. Inline `style=` is reserved for values that genuinely change per render — and even then prefer setting a CSS custom property consumed by a utility or token (see how `tab_wheel.rs` passes `--tw-rot`, `--tw-bx`, `--tw-cr`) rather than restating full property strings. Canvas2D paint strings (`ctx.fillStyle = …` in `sky/render/`) are *not* DOM CSS — leave them inline.

## Offline sky map (planetarium imagery, Framing Assistant, Targets thumbnails)

The sky's imagery is a **local mirror of the CDS `P/DSS2/color` HiPS**: the
whole sky in HEALPix **nested** cells, one 512 × 512 JPEG per cell, orders 0
(12 tiles, ~58°) to 9 (3.1 M tiles, ~0.8″/px); `hips_frame=equatorial`, i.e.
ICRS/J2000. The tree is kept in CDS's exact layout — `properties`, then
`Norder{k}/Dir{(n / 10000) * 10000}/Npix{n}.jpg`, `12·4^k` tiles per order —
so `rsync`, `wget -r` and any HiPS client understand it. Sizes: order 6 ≈
3.3 GB, 7 ≈ 13–20 GB (the default), 8 ≈ 53 GB, 9 ≈ 210 GB; the fine orders
are meant for `--cone` runs around chosen targets, not the full sky. The
browser is remote (a phone on wifi): it computes the cells under its view at
the order matching its zoom and streams **only those tiles** (≤ ~25 per view,
parents first), which the browser keeps for good (`immutable`). Generate with:

```bash
uv run scripts/fetch_skymap.py --max-order 3      # smoke: 1,020 tiles, ~25 MB
uv run scripts/fetch_skymap.py                    # orders 0..7
uv run scripts/fetch_skymap.py --status           # per-order coverage, max_order, panorama
uv run scripts/fetch_skymap.py --allsky           # Milky Way panorama (allsky.jpg + allsky_small.jpg)
uv run scripts/fetch_skymap.py --min-order 8 --max-order 9 --cone 83.82 -5.39 3
uv run scripts/fetch_skymap.py --prune-above 7 | --info-only | --selftest
```

Output goes to `.cache/skymap/` (gitignored — **not** `junos-web/public/`).
`--out` or `SKYMAP_DIR` (the server reads the same variable) moves it; note
`--skymap-dir` is the *server's* flag. Resumable (existing tiles > 1 KB are
skipped, `.part` + `os.replace`, Ctrl-C still writes `info.json`); tiles are
static files on CDS's Apache (no per-request pause needed; `--pace 0.2
--workers 4` is the gentle setting; a 404 is final, 429/5xx back off and
rotate mirrors). The script writes **`info.json`** (also every 60 s during a
run), which the server serves verbatim at `/api/skymap/info`:

```json
{"survey":"CDS/P/DSS2/color","title":"DSS colored","frame":"equatorial",
 "tile_width":512,"tile_format":"jpg","survey_max_order":9,"max_order":7,
 "orders":{"0":12,"1":48,"…":0,"8":1204},"bytes":13968123456,"allsky":true,
 "attribution":"Digitized Sky Survey - STScI/NASA, Colored & Healpixed by CDS",
 "attribution_url":"http://archive.stsci.edu/dss/copyright.html","updated":"2026-10-25T10:12:33Z"}
```

`max_order` is the highest order such that every order up to it holds ≥ 99 %
of its tiles — the zoom the client may rely on everywhere (`null` when even
order 0 is incomplete); partial finer orders stay listed in `orders` so a
client may try them and tolerate a 404. Without `info.json` the server
derives the same shape from a startup scan. The mirror is **optional**:
`max_order: null` → the sky draws symbols over the Milky Way panorama alone
and the Framing Assistant previews the grid over black. `--skymap-online`
fills missing tiles from CDS on demand.

**Packed copy.** `python3 scripts/pack_skymap.py pack` writes
`<skymap>/archive/`: `meta.tar` (`properties`, the two panoramas), one
`Norder{k}_Dir{d}.tar` per HiPS Dir (members `Norder{k}/Dir{d}/Npix*.jpg`,
≤ 10,000 tiles, ~1 GB at order 7, uncompressed) and `manifest.json`
(`format`, `created`, per archive `file`/`order`/`dir`/`tiles`/`bytes`/
`size`/`sha256`/`fingerprint`, `total_size`, the source `info`). The server
serves that folder at `/api/skymap/archive/*`; `pull` on another machine
skips the Dirs already complete locally, resumes, verifies, extracts and
rewrites `info.json`. `pack` after a new fetch rewrites only the changed
Dirs (`status` lists them); `--max-order` limits the set and drops the
archives above it.

**HEALPix helpers live in three places** and must agree bit for bit: Python
(`scripts/fetch_skymap.py`: `ang2pix_nest`, `pix2ang_nest`, `cone_pixels`,
only for `--cone`), Rust (`junos-web/src/healpix.rs`) and WGSL
(`components/sky/shaders/skymap.wgsl`, per pixel). All three are the
healpix_cxx formulas (nested scheme, `phi = RA`, `z = sin Dec`, Morton bit
spread of `(ix, iy)` under `face << 2k`). `--selftest` round-trips every cell
of orders 0–4 and prints the shared vectors the Rust tests assert:
`pix2ang_nest(3, 0) = (45.000000, 4.780192)`, `(3, 767) = (315.000000,
−4.780192)`, `(7, 196607) = (315.000000, −0.298417)`, `(0, 4) = (0, 0)`,
`(1, 47) = (315.000000, −19.471221)`; `ang2pix_nest(3, 83.82, −5.39) = 334`,
`(7, 10.68, 41.27) = 10836`, `(5, 0.0, −89.5) = 8192`.

**Milky Way panorama.** `--allsky` fetches one plate-carrée J2000 panorama
(`CDS/P/Mellinger/color`, via hips2fits, centred on RA 0h, north up, **east
left**: `u = 0.5 − RA/360`), 4096 × 2048 plus a 2048 px `allsky_small.jpg`
for phones / Lite, served at `/api/skymap/allsky*.jpg`. It stays the
wide-field backdrop under the DSS2 layer.

**Client side.** `main.rs` fetches `/api/skymap/info` once into `SkyMapCtx`.
The sky draws the map in a **full-screen pass** (`gpu/layers/skymap.rs` +
`shaders/skymap.wgsl`, after the panorama): per pixel, the shared inverse
projection (`shaders/sky_inverse.wgsl`, concatenated in Rust in front of
both `allsky.wgsl` and `skymap.wgsl` — WGSL has no includes) gives J2000,
`hpx_hash_dxdy` the cell at the view's order, a storage-buffer table
(`slot + 1` per cell, orders 0..=8 flattened at `table_base(o) + hash`,
4 MiB) the resident layer of a 512² `texture_2d_array` atlas (64 layers on
desktop, 40 on phones), and a missing tile falls back to its parent cell
(shift the hash, fold the quadrant bits into dx/dy) down to three orders up —
so a zoom never shows a hole. `render/layers/skymap.rs` is the CPU side:
order = round(log2(58.63° · px/° / 512)) with hysteresis (−0.5 on phones),
cells = `healpix::cone_cells` over the canvas diagonal, kept when the
bounding box of their projected vertices meets the canvas — partially
visible cells included; `project_far_with`, clipped at 90° rather than
1.5 × the radius, since a 16:9 corner lies 2 × out — (≤ 48 / 32) plus
their grandparents (≤ 8 / 6) requested **first**, images through the
`TileImageCache` (6 concurrent loads), ≤ 4 atlas uploads per frame (the
sky stays at full frame rate while any decoded tile waits)
(`MipUploader`, whose `copyExternalImageToTexture` **panics the wasm on a
validation error** — keep its preconditions). The layer crossfades in over
the panorama between 25° and 10° of view radius (`crossfade`), so wide
fields request no tiles at all; brightness is a slider; Lite caps the order
at `max_order − 2`. While it shows, `Frame::image_min_half_px` makes the DSO
layers skip the outline of objects ≥ 10 px (the picture shows them).
Canvas2D fallback: each decoded tile is drawn as affine quads over its
cell (the least-squares fit of its four vertices; `source-over`, ≤ 40
tiles), a quad split into its 4 sub-cells with the matching image
quadrants while the fit misses a vertex or the cell centre by > 1.5 px
(up to 6 splits, ≤ 1,024 quads a frame), since an affine map can't follow
a HEALPix cell through the azimuthal projection — one quad per 3.7° cell
sits 7 px (~3′) off, a visible shift against the catalog stars; a
sub-quad off the canvas is skipped, and each quad bleeds 0.5 px so
neighbours never show a seam. **HiPS orientation**: dx
runs from the cell's south vertex along S→E, dy along S→W, and the JPEG
stores column ← dy, row ← dx (top-left = S, top-right = W, bottom-left = E,
bottom-right = N) — one `uv = vec2(dy, dx)` line in the shader and one
matching line in the sampler; verify against the Tycho-2 stars at ~1°
fields (only one of the eight orientations aligns) after touching either.

The Framing Assistant and the Targets thumbnails reproject on the CPU
(`components/sky/skymap_sampler.rs`): a `CutoutSpec` (J2000 centre, field
across the shorter side, size, rotation; north up / east left at 0, i.e.
`astro::frame_point_eq`) is filled pixel by pixel — inverse TAN →
`hash_dxdy` → the tile's texel from pixels extracted once per tile
(`getImageData`, LRU) — with the same parent fallback, at a bounded
internal size (0.5 Mpx desktop, 0.25 phones) scaled onto the canvas.
`framing.rs`'s `Viewport` is the same TAN plane, so the mosaic grid sits on
the same stars as the image; its label reads "DSS2 · order k · N tiles".
`components/sky_thumb.rs` is a `<canvas>` rendered through the tab's shared
sampler until every tile under the field is in; the Targets rows (128 px at
48 CSS px) and the detail sheet (512 × 288) use it, the kind tag standing in
without a map.

## Static assets

`junos-web/public/` contains three binary catalogs: `junos.bin` (stars to V ~10), `tycho.bin` (the rest of Tycho-2, 2.2 M stars, 13 MB) and `dso.bin` (deep-sky). Trunk copies them into `dist/`. They are checked in — do not regenerate or re-encode them as part of code changes. Each is fetched with a `?v=N` (`fetch_catalog`, `fetch_deep_stars`, `fetch_dso_catalog`) that the server marks immutable and the browser keeps in the Cache API, so **any change to a catalog's bytes must bump its `?v=`** or browsers keep the old file. A `dso.bin` layout change touches two readers (`dso_catalog.rs`, the generator); it is at `v=3` (kind, then `lines` u8 and `con` 3 × ASCII). Most nebulae have no magnitude (99): the sky culls by `Dso::vis_mag`, a size-based stand-in, never by `mag`.

## Code style observed in this codebase

- French and English comments coexist; mirror the surrounding file.
- Commands are dispatched as raw JSON strings; do not introduce a typed command enum in the frontend (junos-guider's engine `Command` is internal to the daemon; the browser still sends `guider_rpc` JSON).
- Arc-clone `SendCmd` aggressively before moving it into closures.
- All three crates build warning-free (junos-guider also with `--features sim` and `--tests`); keep it that way. Where a struct mirrors a wire shape (`ws/types.rs`, `catalog.rs`, `files/types.rs`) or declares strings ahead of the UI (`i18n`), it carries one `#[allow(dead_code)]` and a comment saying why — annotate rather than prune those.
- Debug traces go through `debug_log!`, not `leptos::logging::log!` directly, so they stay out of release builds.
- Tab components should take only the specific signals they need plus `SendCmd`, never `DeviceStore` whole. Use Leptos context only for values that need to cross many components (see `*Ctx` newtypes in `main.rs`).
- junos-guider: English comments; a ported file keeps its `Ported from PHD2 src/…` header and names PHD2's functions and `file.cpp:line` where it follows them; `engine/` stays pure (no I/O, async or wall clock) and PHD2-faithful (pitfall 24); engine changes carry unit tests, against goldens from PHD2 where it matters.

## Working rules

- **Keep it simple.** Don't over-engineer: the smallest code that does the job, plain comments, plain docs. No abstractions, options or generality beyond what the request needs.
- **Structure the work as several commits.** The code is reviewed commit by commit: one logical change per commit (e.g. store/wire first, then the UI, then docs), each building and warning-free on its own, with a clear message.
